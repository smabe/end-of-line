# sqlite-migration-p5 — queue + quota tables; retire the corruption-repair subsystem

You are phase `p5` of the `sqlite-migration` plan. This phase delivers, as one commit, the last two per-project JSON stores — `queue.json` and `quota.json` — moved into the project DB, the queue-pop sequence made transactional, the queue corruption-repair subsystem deleted (its failure mode is structurally impossible in SQLite), and the `clu quota clear` operator affordance.

## Locked decisions (do NOT re-litigate)
See the master `plans/sqlite-migration.md`. The decisions binding this phase:
- Queue/quota live in the project DB (`queue`, `queue_history`, `quota` tables per p1 DDL). Pop = one project-DB transaction (create plan rows + move queue head to history/delete), then the host-DB register transaction — two coordinated txns, the recovery shape the upstream decision #1 names verbatim.
- "Row absent == not paused" replaces "file absent == not paused" (quota singleton row, `id=1`). The operator escape hatch becomes `clu quota clear` (upstream #5); `rm quota.json` dies with the file.
- The repair subsystem is DELETED, not ported: `queue.py:56-190` (byte-regex slug rescue, `validate_repair`, throttle files), `cli.py:_handle_corrupt_queue`, `dispatch.dispatch_repair_worker`, and the `KIND_QUEUE_CORRUPT`/`KIND_QUEUE_REPAIRED`/`KIND_QUEUE_REPAIR_FAILED` notify kinds + renderers. Justification carried from research: the machinery exists because partially-written JSON is recoverable text (B1: "~70% of a module named queue"; A2: the pipeline is premised on text) — a WAL DB never presents a half-written store, and a corrupted DB file is not worker-editable anyway.
- `dispatch.repair_command` config field: accepted and ignored (config parsing stays tolerant; a `.orchestrator.json` naming it must not start failing), with a one-line deprecation note in p8's docs.

## Decisions & findings

### Decision: queue-pop is two transactions (project, then host), not one distributed one  *(status: active)*
- **Rationale:** operator-decided topology (upstream #1 names this recovery shape verbatim). Crash between the two leaves a created-but-unregistered plan — the same window today's flock nesting leaves, already healed by the zombie sweep / re-run pop (`cross_plan_rules.py:199-201` documents replayability; `registry.register` is idempotent).
- **Alternatives considered:** ATTACH the host DB into the project connection for one txn — rejected: cross-DB transactions under WAL are not atomic across files anyway (each DB commits its own WAL), so ATTACH buys syntax, not atomicity.
- **Evidence:** design brief §5.1; cross_plan_rules.py:199-219; registry.register idempotence (`registry.py:64-84`).

### Decision: delete the repair subsystem rather than adapt it to DB corruption  *(status: active)*
- **Rationale:** the subsystem's premise is text-recoverability of a torn write; WAL removes torn writes, and a genuinely corrupted binary DB (disk failure) is not something a headless Claude worker edits back to health. The tolerant-read contract (skip + stderr) plus 0-byte/absent-DB recreation covers the residual.
- **Alternatives considered:** port `validate_repair` to dump-edit-reimport (machinery without a failure mode to serve).
- **Evidence:** queue.py:1-18 (the module's own framing), B1/A2 research findings (master Background findings).

## Failure modes to anticipate
- The busy-gate reads plan snapshots gathered OUTSIDE the pop txn (`load_plans_for_project`) — same TOCTOU as today (A3 #3); unchanged risk, cron remains the sole ticker. Do not try to fix it here (parked scope).
- `queue add --batch` (`cli.py:3192`) writes several entries + a batch dry-merge gate interaction — keep the batch insert one txn so a half-added batch can't exist.
- Two ticks racing the pop: `pop_head_if`'s WHERE-head guard must make the loser a no-op, not a duplicate plan-create — plan-create runs in the same txn, and `plan_store.create` on an existing slug raises (IntegrityError → exists) exactly like today's exists() guard.
- Demo mode does NOT seed a queue — verified this session, `demo.py` writes config, plan markdown and state only, so there is no demo queue path to migrate. (Recorded as a closed question rather than a risk; it was hedged at drafting and is now checked.)
- Deleting notify kinds: `clu watch`'s formatters don't reference queue-corrupt kinds (they are notify-kinds, not events) — but grep for the kind strings across tests and docs before deleting.

## Done criteria
- **Escalated at p3 — every tolerant `except` clause this phase touches or adds is checked against what the STORE can raise.** This class has now recurred twice: p2 found eight `except OSError` guards that a database failure would have walked straight through, and p3 widened four more and STILL missed the zombie sweep's two, which its review caught. The shape is always the same — a clause that was complete for a FILE is incomplete for a database, because a broken store arrives as `sqlite3.Error`, contention as `db.DbBusy` (a `RuntimeError`, so `except OSError` misses it), and a newer schema as `db.SchemaTooNew`. The check: for every `except` guarding a store read or write in this phase's files, say which clauses were examined, which were widened, and which were deliberately left narrow and why. `db.DEGRADABLE_ERRORS` is the tuple for "degrade rather than fail"; it deliberately excludes the `RuntimeError` raised when WAL did not take.
- Observable: end-to-end pop test — seed queue with two plans, run the advancement rule twice; first pop creates plan rows + registers + moves head to history with outcome recorded; second respects the busy gate. Two-process race test: both poppers run, exactly one head consumed.
- Observable: the scripted demo sequence (p1's `tests/demo_script.py`) runs end-to-end and the project's `.orchestrator/` afterwards contains ZERO `queue.json`, `quota.json`, `*.state.json` and `*.lock` files — this phase is where the master's plan-level zero-file criterion actually becomes checkable, since p3 could only assert the state half.
