# sqlite-migration-p6 — supervisor tick restructure: snapshot → detect → CAS apply

You are phase `p6` of the `sqlite-migration` plan. This phase delivers, as one commit, the supervisor tick rebuilt for the DB: all subprocess work (ps walks, lsof, killpg reaps, coolant) runs OUTSIDE any transaction against a read snapshot, and the tick's mutations land in ONE `BEGIN IMMEDIATE` transaction guarded by preconditions — the specific facts the tick's decision rested on, re-asserted inside that transaction (NOT a whole-plan version counter; see Locked decisions). Today the tick holds the exclusive state lock across seconds of subprocess work (`supervisor.py:614-625` + the reap escalation loop `state.py:436-457`) — under WAL's single-writer rule that shape would starve every callback, so this restructure is a correctness requirement, not a cleanup.

## Locked decisions (do NOT re-litigate)
See the master `plans/sqlite-migration.md`. The decisions binding this phase:
- **Tick shape — DECIDED (operator delegated the call at approval 2026-08-19): snapshot → detect → ONE end-of-tick transaction, guarded by PRECONDITIONS, not by a whole-plan version counter.** The tick reads one snapshot, computes every state delta as data (events to append, claim fields to set, status flips, releases), and applies them in a single `db.write_txn` whose WHERE clauses re-assert only the facts its decision actually rested on. Any precondition that no longer holds → `TickResult("idle", "concurrent_write")`, and the 30s cron re-drives. **A blunt `plans.version` CAS is specifically rejected — see the Decision entry; it would abort most watchdog ticks against exactly the plans that need watching.**
- The precondition vocabulary, and what each one protects (this list IS the contract — a detection path that needs a precondition not on it must add it rather than widen an existing one):
  - `expect_claim` — the claim's `(claimed_by, phase_id)`, or the assertion that no claim row exists. Guards every lifecycle decision: lease-expiry release, dead-PID release, dispatch, plan-done.
  - `expect_max_event_id` — the highest `events.id` the snapshot saw. Guards every decision derived from the event log: attempts budget, completed-phase set, halt-on-max-attempts, plan-done. **Heartbeats and activity stamps write no events** (`state.py:785-794` for the heartbeat's deliberate no-event contract), so the two highest-frequency writers never trip this.
  - `expect_claim_fields` — the specific claim columns a gap-fill emitter judged: `last_heartbeat_at` for the stalled emit, `active_tool_started_at` for the worker-idle and stuck-tool emits. A heartbeat landing mid-tick correctly cancels a stalled emit; a Bash call starting mid-tick correctly cancels an idle emit. That is the precondition doing its job, not a spurious abort.
  - `expect_blocker_state` — the `(blocker_id, answer IS NULL, consumed)` facts the SLA-escalation and answered-blocker paths read.
  - `expect_status` — the plan status the decision assumed, for paths that flip it.
- `plans.version` still exists and every writer still bumps it, but its job is **reader-facing change detection** (per-plan "did this plan change" for watch/top, one granularity finer than `PRAGMA data_version`). It is not the tick's correctness guard.
- One tick = one action is UNCHANGED (project convention, CLAUDE.md): the priority chain, its ordering, and TickResult semantics survive; only the I/O shape changes.
- Subprocess ordering contract preserved: durable state commits FIRST, best-effort reaps/coolant fire AFTER commit (the order `supervisor.py:731-752` documents; p4 already moved coolant post-txn for callbacks).
- Notify stays post-lock: `TickResult.notify_body` / `side_notifies` dispatch after the txn exits, exactly as `cmd_tick` does today — never inside it.

     ```python
     @dataclass
     class TickDelta:
         events: list[dict]                 # to append
         claim_updates: dict[str, object]   # fields to set on the live claim (CAS on claimed_by)
         release_claim: bool

         expect_max_event_id: int | None             # highest events.id at snapshot time
         expect_claim_fields: dict[str, object]      # e.g. {"last_heartbeat_at": "...Z"}
         expect_blocker_state: dict[str, tuple[bool, bool]]   # blocker_id -> (unanswered, consumed)
         expect_status: str | None
     def apply_tick_delta(orch_dir, slug, pre: TickPreconditions, delta: TickDelta) -> str | None
         # ONE write_txn. Re-assert every non-None precondition as a WHERE/SELECT check
         # INSIDE the txn; any mismatch raises TickConflict and nothing is written.
         # Returns the claim token on a dispatch action.
     ```

## Decisions & findings

### Decision: one end-of-tick transaction, guarded by preconditions rather than a whole-plan version  *(status: active — the operator delegated this call at approval 2026-08-19)*
- **Rationale, part one — why ONE transaction at the end.** The tick is first-match-wins with gap-fill side effects riding along. A single delta application keeps "one tick = one action" (the project's `docs/adr/0002` convention) literally one atomic write, and makes the conflict story trivial: nothing was written, so nothing was half-written, and detection is cheap enough to redo. Per-priority writes would take up to five transactions per tick with re-validation between each, opening five contention windows instead of one and making a half-applied tick reachable.
- **Rationale, part two — why NOT `plans.version`, which is what I first drafted.** Working the decision through the actual write rates killed my own default. A whole-plan version counter is bumped by EVERY writer, and the two highest-frequency writers fire against precisely the plans a watchdog tick cares about: the heartbeat daemon every 120s, and — **on any host where the operator has installed the activity hook** — a stamp on every Bash tool call the worker makes (`clu activity --start-bash`, matcher `"Bash"`, `end_of_line/skills/clu-phase/SKILL.md:302`; the write path is `state.py:1090-1122`). The hook is operator-installed and token-guarded, so a host without it produces no stamps at all; the heartbeat every 120s remains unconditional. The argument therefore rests on the heartbeat alone at minimum, and gets far stronger wherever the hook is installed — which is this host, and is the configuration the wedge-detection features were built for. The tick's detection window is seconds wide — it shells out to `ps` (5s timeout) and `lsof` (1s). So a version CAS would abort a large share of ticks against any actively-building worker, and the aborted paths are exactly the watchdogs (stalled, dead-PID, lease expiry, stuck tool) whose whole job is to notice that worker is in trouble. A guard that fails most often on the plans it most needs to guard is the wrong guard.
- **Rationale, part three — why preconditions are the right abstraction.** The version counter is a blind layer: it cannot tell "the claim was released" from "a heartbeat landed", so it must treat both as invalidating. Passing the tick the facts its decision actually rested on removes the blindness rather than tuning around it. A heartbeat no longer aborts a lease-expiry release (it does not move `lease_expires`), and it still correctly cancels a stalled-emit (which judged that very timestamp). The load-bearing detail that makes this work: heartbeats and activity stamps write **no events**, so `expect_max_event_id` — the guard for every event-log-derived decision — is untouched by them by construction.
- **Alternatives considered:** (1) `plans.version` CAS — rejected above on write-rate grounds; kept in the schema as a reader-facing change hint, which is a real job it does well. (2) Per-priority CAS writes — rejected on contention windows and partial application. (3) One `BEGIN IMMEDIATE` held across the whole tick including subprocess work — rejected outright: WAL allows one writer, and a reap escalation loop runs up to ~5s (`state.py:436-457`), so this reproduces today's flock starvation with extra steps. (4) Re-reading and re-deciding inside the transaction (no preconditions, just recompute) — rejected: the decision depends on `ps`/`lsof` output, which cannot be gathered inside a transaction without reintroducing (3).
- **Evidence:** B2's from-scratch shape ("read-snapshot → compute (ps/lsof/reap outside any transaction) → versioned CAS write") — adopted, with the guard sharpened; probes this session: `BEGIN IMMEDIATE` + busy_timeout is lossless under contention while long holds pin the WAL (master Background findings); `supervisor.py:614-625` (today's in-lock subprocess work); `state.py:785-794` (the heartbeat's deliberate no-event contract, which is what makes `expect_max_event_id` immune to it).

### Decision: a conflicted tick drops its gap-fill notifies rather than sending them  *(status: active)*
- **Rationale:** the dedup markers that prevent re-notification commit in the same txn as the action; sending a notify whose marker never committed double-pings on the retry. Detection is cheap and re-runs in 30s.
- **Alternatives considered:** send-then-mark (double-ping risk), mark-in-separate-txn (a marker without its event lies).
- **Evidence:** marker fields and their dedup contracts, `state.py:983-1031`.

## Failure modes to anticipate
- A detection helper that still mutates the snapshot dict in place (today all four emitters do; `_detect_stalled` mutates the claim then returns a TickResult) and whose mutation silently never reaches the delta — the restructure must convert all five; grep for `data[`/`claim[` writes in supervisor.py afterwards as a mechanical check.
- `attempts_for_phase` and `completed_phase_ids` are O(events) scans over the snapshot — unchanged behavior; do NOT convert them to SQL here (p7/parked; correctness first).
- The lease-expiry branch reads `claim.log_path` for quota classification BEFORE release (`supervisor.py:637,715` comments) — in delta form the snapshot still carries it; keep the read-before-release ordering in detection.
- The dispatch action's token is generated inside `apply_tick_delta` (claim insert) but `dispatch_for_tick` needs it after — return it from apply; the Popen + `_stamp_pid` flow (p4 ops) is unchanged and remains outside the txn.
- Plan-file parsing (`parse_sessions_index`, `supervisor.py:843`) reads markdown from disk — fine outside the txn, but its absence error path (`TickResult("error")`) must not require a write.
- A `TickConflict` raised INSIDE `cmd_tick_all`'s loop must not abort the loop — the per-plan try/except that guards it lives in `cmd_tick_all` (`cli.py:4046+`), not in `_tick_one_plan`.

## Done criteria
- **Carried in from p5's sweep — decide, in writing, whether `db.write_txn`'s nested-join stays.** p5 added it because the tick consults the quota gate from inside its own state window and SQLite's write lock is per-connection, so the second `BEGIN IMMEDIATE` waits for a lock only the waiter can release (reproduced: `DbBusy` after 1.10s at a 1s budget). This phase's whole purpose is that the tick no longer holds a transaction across detection, which removes the nesting that made the join necessary. Two costs to weigh rather than inherit: `with db.write_txn(...)` no longer guarantees a commit at block exit, and any future accidental nesting joins silently instead of failing loudly. Observable: either the join is removed and a test proves the tick nests no transactions, or the Decisions entry records why it stays as a safety net and names what still nests.
- **Carried in from p4's sweep — a test asserting a timestamp column equals a just-computed value MUST backdate first.** `st.utcnow()` is second-resolution: three consecutive calls return the identical string, so a test that seeds a row and immediately asserts `row[field] == op(...)` compares a value to itself and passes whatever the op wrote, including nothing and including the wrong column. p4 proved this rather than supposing it — breaking `op_heartbeat` to write the neighbouring column left all 53 tests in its own file green and the full suite green. Observable: any new test in this phase asserting on a written timestamp seeds a distinctly old value first, asserts the value ADVANCED, and asserts the neighbouring column is untouched.
- **Carried in from p4's sweep — no git subprocess runs inside an open transaction.** `_maybe_cleanup_worktree` shells out to git several times from inside a `st.mutate` window, reached from `cmd_complete` and `_perform_archive`; p4 moved the `cmd_complete` copy after its commit but could not restructure the archive path without a plan-field op it did not own. That is the project-wide lock held across foreign work — p2's finding, and the exact shape this migration exists to remove. Observable: a trace or a read of the archive path shows no `subprocess` call between BEGIN and COMMIT.
- **Escalated at p3 — every tolerant `except` clause this phase touches or adds is checked against what the STORE can raise.** This class has now recurred twice: p2 found eight `except OSError` guards that a database failure would have walked straight through, and p3 widened four more and STILL missed the zombie sweep's two, which its review caught. The shape is always the same — a clause that was complete for a FILE is incomplete for a database, because a broken store arrives as `sqlite3.Error`, contention as `db.DbBusy` (a `RuntimeError`, so `except OSError` misses it), and a newer schema as `db.SchemaTooNew`. The check: for every `except` guarding a store read or write in this phase's files, say which clauses were examined, which were widened, and which were deliberately left narrow and why. `db.DEGRADABLE_ERRORS` is the tuple for "degrade rather than fail"; it deliberately excludes the `RuntimeError` raised when WAL did not take.
- Observable: the trace test proves zero subprocess seams execute between BEGIN and COMMIT of the apply txn (assertion output pasted into Status).
- Observable: precondition-conflict test — a `clu complete` callback commits between snapshot and apply → the tick returns `[idle] concurrent_write`, the callback's write is intact, and the SAME action succeeds on the following tick.
- Observable: **precondition-selectivity test, the one that proves the guard is not blunt** — with a live claim, fire (a) a heartbeat and (b) an activity stamp between snapshot and apply, then apply a lease-expiry delta: it COMMITS (neither writer touched `lease_expires` or the event log). The same test with a stalled-emit delta ABORTS after the heartbeat, because that emit judged `last_heartbeat_at`. Both directions asserted in one test; a guard that fails the first half is a `plans.version` CAS in disguise.
- Observable: the scripted demo sequence (p1's `tests/demo_script.py`) under the restructured tick — dispatch, stalled detection, blocker round-trip, completion — with `clu watch` emitting a non-empty stream that diffs clean against `tests/goldens/watch-demo.txt` (p1's pre-migration capture; the same golden p3 and p7 use).
- The four gap-fill emitters plus `_detect_stalled` produce identical events/side_notifies for identical snapshots as before the restructure — table-driven parity tests over seeded states, each case asserting the expected event list is NON-EMPTY before comparing (a parity test where both sides are empty proves nothing, and a restructure that silently stopped emitting would pass it).
- **Carried in from p1's sweep — the `phase_started` event still carries NO `attempts` key.** Same constraint p4 carries, for the same reason and with a second route into it: this phase rebuilds events as tick deltas, so a delta constructed from the claim's own fields could pick up the attempt count that the file-engine event never had. `clu watch` prints `attempt 1` for every attempt (`state.py:762`, `watch.py:121,334`) and p1's golden froze that, so gaining the key here breaks this phase's own golden diff above. Assert it: the delta's start event has no `attempts` key.
